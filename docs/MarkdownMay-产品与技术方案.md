# 马冬梅（Markdown May）产品与技术方案

> 文档状态：初稿
> 目标平台：Windows 10 / Windows 11，64 位
> 产品定位：面向普通办公人员，尤其是财务、行政等非开发用户的轻量 Markdown 编辑与阅读工具

## 0. 原文意见汇总与处理结论

原文中的意见可以归纳为以下产品决策。这些决策是后续设计和开发的硬约束，不再作为待讨论项：

1. **产品就是 Markdown 记事本**，不是“首先像记事本”，也不向知识库、协作平台或开发工具扩张。
2. **永久不做账号、登录和云服务**。
3. **永久不做应用内检查更新**。版本发布由开源代码托管平台承担，程序本身不联网检查版本。
4. **默认渲染模式必须所见即所得**。同时提供可编辑源码模式，以及左侧源码可编辑、右侧渲染只读的对照模式。
5. **图片是必需功能**。记事本式的简单不等于只能处理纯文字；插入、显示、复制、删除和保存图片引用均属于正式范围。
6. **必须导出 PDF 和 Word**。
7. 功能范围按版本形成受控基线，再按瀑布流程逐层实现和验收；用户可以增加功能，但必须先做全局影响分析并形成新版需求基线。

因此，Scintilla 不作为所见即所得主编辑器，但可以作为源码编辑表面；RichEdit 承担渲染模式的所见即所得编辑。PDF 和 DOCX 导出属于正式范围。

## 1. 产品目标

马冬梅不是缩小版 VS Code，也不追求成为功能繁杂的知识管理平台。**它就是一个支持 Markdown、图片和文档导出的现代记事本**：

- 双击 Markdown 文件就能快速打开；
- 默认中文界面，不要求安装插件或配置环境；
- 能直接阅读，也能随时编辑；
- 安装包和程序体积小，内存占用低；
- 免费、开源，无账号、无广告、无联网依赖；
- 操作符合 Windows 办公软件习惯。

“秒开”不机械地定义为某个固定毫秒数，而是指用户双击常见文档后几乎感觉不到等待。建议将性能目标定为：

| 场景 | 目标 |
| --- | --- |
| 冷启动并打开普通文档（小于 1 MB） | 主窗口 300 ms 内可见，500 ms 内可操作 |
| 热启动 | 200 ms 内可操作 |
| 常驻内存（普通文档） | 尽量控制在 40 MB 内 |
| 发布体积 | 便携版单个 EXE，目标 10 MB 内；第一阶段允许略高 |
| 大文件 | 10 MB 文件能打开和编辑，不崩溃；解析和高亮不得长时间阻塞界面 |

这些是工程目标，不是对首版的硬性承诺，最终以基准测试结果为准。

## 2. 目标用户与典型场景

### 2.1 目标用户

- 财务、行政、人事、运营等办公人员；
- 只想阅读项目说明、制度、报表备注等 `.md` 文件的人；
- 希望用简洁工具记录结构化文字，但不愿学习开发工具的人；
- 需要便携、无账号、可离线工具的个人和企业用户。

### 2.2 典型场景

1. 用户在资源管理器中双击 `.md` 文件，直接进入阅读视图。
2. 用户点击“编辑”或按快捷键，切换到编辑视图并修改内容。
3. 用户新建文档，使用标题、列表、表格、待办事项等常用格式。
4. 用户保存后导出或复制为 HTML/PDF，交给不使用 Markdown 的同事。
5. 用户在设置中将马冬梅注册为 `.md`、`.markdown` 的默认候选程序。

## 3. 设计原则

### 3.1 默认简单

- 默认中文，不出现开发术语；
- 不存在账号和登录功能；
- 阅读优先：从资源管理器打开文件时默认展示渲染结果；
- 常用格式通过工具栏和快捷键完成，用户不必背 Markdown 语法；
- 高级功能放在菜单和设置中，不占据主界面。

### 3.2 原生、轻量、离线

- 不使用 Electron、WebView2、CEF 或 Qt WebEngine；
- 不捆绑浏览器内核；
- 核心编辑、解析和渲染全部在本地完成；
- 不提供检查更新功能；程序正常工作完全不需要网络；

### 3.3 文件是唯一真相

- 使用普通文本文件，不建立私有数据库；
- 不改变用户目录结构，不锁定用户；
- 自动保存只作为崩溃恢复手段，不替代显式保存；
- 对外部修改、编码、换行符和未保存状态给出明确提示。

## 4. 技术选型

### 4.1 候选方案对比

| 方案 | 启动与体积 | 中文输入与原生体验 | 开发难度 | 结论 |
| --- | --- | --- | --- | --- |
| Electron / WebView2 | 差，运行时和内存开销大 | 可接受 | 前端开发容易 | 与核心目标冲突，排除 |
| Go + Fyne/Gio | 中等，通常可做单文件 | 控件、输入法、无障碍和字体细节存在风险 | 中等 | 适合跨平台工具，不适合作为本项目首选 |
| C# + WPF | 启动尚可；自包含发布体积较大 | 成熟 | 较低 | 可作为快速验证方案，不作为最终轻量路线 |
| Rust + egui/iced | 体积较小 | 非原生文本编辑、输入法及无障碍仍需大量打磨 | 中高 | 不建议用即时模式 GUI 做办公编辑器 |
| Rust + Win32/DirectWrite | 小且快 | 原生能力好 | 高，Windows API 开发较繁琐 | 可行，但生态整合成本高于 C++ |
| C++ + Win32 + DirectWrite | 最容易实现小体积和快速启动 | 最佳 | 高 | **推荐** |

### 4.2 推荐结论

首个平台明确为 Windows，推荐使用：

- **语言：C++20**
- **窗口与系统集成：Win32 API**
- **所见即所得编辑内核：Windows RichEdit（`msftedit.dll`，系统组件）**
- **源码编辑内核：Scintilla，静态链接**
- **Markdown 解析：MD4C，静态链接**
- **排版补充与图片绘制：Direct2D + DirectWrite + Windows Imaging Component**
- **构建系统：CMake + MSVC**
- **配置格式：UTF-8 JSON 或简单 INI**
- **安装包：Inno Setup 或 WiX；同时发布免安装单 EXE**

选择 C++ 并不是因为其他语言“做不到”，而是本项目的优先级非常明确：Windows 原生文本体验、启动速度、小体积、单文件发布。C++ 能直接使用系统已有的窗口、字体、输入法、打印和文件关联能力，也能把 MD4C、DOCX/PDF 导出代码和资源静态编译进一个 EXE。

Rust 的内存安全很有价值，但它不会自动解决 Windows GUI、中文输入、无障碍和富文本排版问题。使用 Rust 仍需直接面对 Win32/DirectWrite，首版开发成本更高。若未来核心团队更熟悉 Rust，可以将解析、文档模型等无 UI 模块逐步改用 Rust，而不是一开始承担额外整合风险。

### 4.3 所见即所得技术修订

Scintilla 是成熟的源码编辑控件，但它的文档本质是纯文本，不适合作为渲染模式的编辑器：隐藏 Markdown 标记后仍要正确处理光标、选区、图片、表格、段落高度和中文输入法，改造成本可能高于自建编辑器。它适合承担源码模式和对照模式左栏。

修订后的方案使用 Windows 自带的 RichEdit 作为输入、选区、输入法、撤销重做和基础富文本排版层，通过 TOM（Text Object Model）访问文本范围。应用维护两种相互映射的表示：

- **Markdown 语义文档**：标题、段落、行内样式、列表、表格、图片等节点，是保存和导出的依据；
- **RichEdit 投影视图**：用户实际看到和编辑的富文本，不展示 `#`、`**` 等语法标记。

打开文件时执行“Markdown → 语义文档 → RichEdit 投影”；编辑命令和输入事件更新语义文档；保存时执行“语义文档 → 规范化 Markdown”。这意味着首次保存后可能规范化部分等价写法，例如列表缩进和表格分隔线。必须通过测试保证内容语义、图片地址和不认识的原始块不会丢失。

对于 RichEdit 无法可靠表达的结构，使用自定义对象或受控降级：

- 图片通过 OLE 嵌入对象显示，Markdown 中仍保存相对或绝对路径；
- 表格首选 RichEdit 表格能力；无法兼容时使用自定义块对象；
- 代码块使用等宽字体、背景和禁止行内格式的独立段落；
- 原始 HTML 和未知扩展使用“原始内容块”保留，不执行其中内容；
- 渲染模式使用 RichEdit；源码模式使用 Scintilla；对照模式左侧使用 Scintilla、右侧使用只读 RichEdit 投影；
- 三种模式共享同一文档会话，通过明确的同步状态机保持源码、语义模型和渲染投影一致。

### 4.4 C++ 代码量估算

以下估算只计算本项目自行维护的 C/C++、资源脚本和测试代码，不计算 MD4C 等第三方库，也不计算生成文件。以非空、非纯注释的物理行为粗略口径：

| 模块 | 预计代码量 |
| --- | ---: |
| 程序外壳、窗口、菜单、模式切换、命令路由 | 5,000～8,000 行 |
| 文档模型、Markdown 导入与无损/规范化输出 | 7,000～11,000 行 |
| RichEdit 所见即所得投影、光标映射、输入与撤销 | 10,000～16,000 行 |
| Scintilla 源码编辑、对照视图和三模式同步 | 5,000～8,000 行 |
| 标题、列表、表格、代码块、链接和图片交互 | 6,000～10,000 行 |
| 文件读写、编码、恢复、外部变更 | 3,000～5,000 行 |
| PDF 与 DOCX 导出 | 6,000～10,000 行 |
| 文件关联、单实例、DPI、主题和系统集成 | 3,000～5,000 行 |
| 设置、对话框、资源与错误处理 | 3,000～5,000 行 |
| 自动化测试、测试工具和基准 | 10,000～16,000 行 |
| **合计** | **58,000～95,000 行** |

较可信的中心估算是约 **75,000 行**，其中产品代码约 57,000 行、测试约 18,000 行。若要求 Markdown 源码逐字符原样往返、复杂嵌套表格、浮动图片、页眉页脚或高度兼容 Word，代码量可能超过 100,000 行。

AI 可以提高代码产出速度，但不能按生成速度估算项目规模。所见即所得编辑器最耗时的是状态一致性和边界测试，而不是把类和函数写出来。

## 5. 总体架构

```text
┌──────────────────────────────────────────────┐
│                  Win32 外壳                  │
│ 菜单 / 工具栏 / 状态栏 / 文档容器 / 对话框  │
├───────────────────┬──────────────────────────┤
│ RichEdit 渲染编辑 │ Scintilla 源码/对照左栏      │
│ 输入/排版/对象    │ 源码输入/高亮/错误定位        │
├───────────────────┴──────────────────────────┤
│ 三模式同步状态机：源码 ⇄ 语义模型 ⇄ 渲染投影    │
├──────────────────────────────────────────────┤
│ Markdown 语义模型：解析、编辑命令、序列化、导出 │
├──────────────────────────────────────────────┤
│ 文件服务 / 设置 / 恢复 / 最近文件 / 系统集成 │
└──────────────────────────────────────────────┘
```

### 5.1 技术无关的模块边界

“应用外壳、编辑器、文档、Markdown、平台服务、导出和测试”这些职责本身与语言基本无关；更换 C++、Rust 或 C# 时，目录名称可以保留。与技术相关的是各模块内部的实现，例如本方案的 `richedit_*`、`win32_*` 和 COM 封装。依赖方向固定为：

```text
app/ui → editor → document → markdown
   │          └────────────→ export
   └───────────────────────→ platform/services
```

- `markdown` 不依赖窗口、RichEdit 或 Win32；
- `document` 不依赖具体窗口；
- `editor` 可以依赖 `document`，反向禁止；
- `ui` 不直接读写磁盘、注册表或生成导出文件；
- `export` 只读取语义文档，不从屏幕截图生成文件；
- 跨模块调用通过明确接口完成，不建立万能 `utils.cpp`。

## 6. 编辑与阅读方案

### 6.1 为什么不使用 HTML 浏览器编辑器

浏览器编辑器实现 Markdown 样式很方便，但会引入 WebView2 运行时、进程和启动成本，也使程序更像一个网页容器。马冬梅的所见即所得表面应直接把 Markdown 解析结果映射为原生排版元素：

- 段落、标题、引用、代码块；
- 有序列表、无序列表、任务列表；
- 粗体、斜体、删除线、行内代码；
- 链接和图片；
- 表格；
- 分隔线。

MD4C 负责解析，不负责显示；RichEdit 承担输入、光标和主要排版，DirectWrite/Direct2D/WIC 补充字体度量、绘制和图片解码。

### 6.2 三种文档模式

程序提供三个模式：

1. **渲染模式**：默认模式，Markdown 标记隐藏，用户直接在排版结果中所见即所得编辑；图片和表格均可原位操作。
2. **源码模式**：不渲染格式，显示完整 Markdown 源文并允许编辑，提供基础语法高亮和错误定位。
3. **对照模式**：左栏为可编辑源码，右栏为只读渲染结果；左侧修改后右侧自动更新。

三种模式是同一个文档的不同表达，不是三份副本。模式切换必须保留未保存状态，并尽量恢复到同一内容附近。

### 6.3 三模式同步策略

- 文件加载后同时建立 Markdown 源文本和已验证的语义文档；
- 渲染模式的编辑以语义模型为权威，提交事务后生成最新 Markdown 源文；
- 源码模式和对照模式左栏编辑时，以源码文本为临时权威，防抖解析成功后更新语义模型和渲染投影；
- 源码存在语法错误时允许继续编辑和保存源码，但右侧必须显示明确错误状态，不得把旧渲染伪装成当前内容；
- 切换到渲染模式前，如果源码无法形成安全语义模型，应留在源码/对照模式并提示错误；
- 源码无法解析时禁用 PDF/DOCX 导出，禁止导出旧语义模型对应的内容；
- 三种模式共享文档修改版本号；保存和导出必须声明读取的具体版本；
- 模式切换前提交 IME 组合输入和当前编辑事务；
- 普通文字输入尽量局部更新，不在每次按键后重建整篇文档；
- 保存前执行适合当前权威表示的校验，禁止把模型失步状态写入文件；
- 超大文档可以延迟非可见图片解码，但不得改变编辑语义。

## 9. 文件关联与发布

### 9.1 单 EXE 与默认程序注册

**可以做到：一个 EXE 放在任意有读取权限的位置，运行后把自己注册为 Markdown 的打开程序候选项。** 不需要 DLL、不需要安装器，也不需要管理员权限。程序读取自身的绝对路径，并在当前用户注册表 `HKCU\Software\Classes` 下登记 ProgID、图标和打开命令，例如：

```text
"D:\任意目录\MarkdownMay.exe" "%1"
```

随后打开 Windows“默认应用”界面，由用户确认将 `.md` 和 `.markdown` 交给马冬梅。Windows 10/11 不允许普通程序可靠、合规地静默抢占默认应用，因此最后的用户确认不能省略。

这里有一个物理限制：注册表记录的是 EXE **注册当时的绝对路径**。注册完成后如果用户移动或重命名 EXE，旧关联一定会失效；Windows 不会自动追踪被移动的普通文件。解决规则如下：

1. EXE 在任何目录第一次运行都可以注册；
2. 每次启动检查已注册路径是否等于当前路径；
3. 如果文件被移动，提示“程序位置已改变，是否修复打开方式”；用户确认后覆盖为新路径；
4. 设置中提供“注册为 Markdown 打开程序”和“撤销注册”；
5. 若用户删除 EXE 而未撤销，系统会留下失效候选项，这是所有免安装单文件程序共有的限制。

因此，“放哪里都能运行并注册”可以实现；“注册后随意移动，关联仍自动有效”无法实现。若用户希望文件关联长期稳定，说明书应建议把 EXE 放在固定目录，例如 `%LOCALAPPDATA%\Programs\MarkdownMay\`，但程序不强制搬移自身。

设置和恢复数据不能写入 EXE 内部。默认写入 `%LOCALAPPDATA%\MarkdownMay\`；这样 EXE 仍是唯一程序文件，且放在只读目录也能工作。若坚持所有可写数据跟随程序，可提供同目录 `MarkdownMay.portable` 标志，但这会多出一个配置文件，也可能因目录无写权限而失败。

### 9.2 单实例策略

默认采用单实例、单活动文档：

- 第二次双击文件时，将文件路径发送给已有进程；
- 已有窗口被激活，并在处理当前文档未保存状态后打开新文件；
- 同时收到多个路径时进入待打开队列，不得静默丢弃；
- 进程间通信使用命名管道；
- 必须正确处理不同权限级别和路径中包含空格、中文的情况。

## 10. 安全与稳定性

- Markdown 默认视为不可信输入；
- 不执行脚本，不加载 HTML 中的活动内容；
- 第一版默认禁用原始 HTML，或仅以纯文本展示；
- 外部链接打开前可按设置确认；
- 图片只从本地路径加载；远程图片永不下载、缓存或显示，只保留地址并显示占位符；
- 保存采用“同目录临时文件写入 + 原子替换”，尽量避免断电损坏；
- 自动恢复文件与原文件分离，并提供清理策略；
- 崩溃日志不得包含文档正文；
- 第三方依赖保持少而稳定，并记录许可证。

## 11. 性能设计与验收

### 11.1 性能原则

- 程序启动阶段不扫描目录、不检查更新、不预加载全部字体；
- 首帧先显示窗口，文档投影和非可见图片解码按需完成；
- 图标使用资源编译进 EXE，不读取大量零散资源文件；
- 设置文件保持很小，延迟加载最近文件缩略信息；
- 图片按可见区域解码并限制最大尺寸；
- Markdown 解析和图片解码不占用 UI 线程；
- 对长行、超大表格、超大代码块设保护阈值。

### 11.2 基准文档

仓库应维护固定测试样本：

- 10 KB 普通中文文档；
- 1 MB 混合格式文档；
- 10 MB 纯文本和长行文档；
- 1000 行表格；
- 大量标题、链接、任务项和本地图片；
- 非 UTF-8、损坏编码、异常换行符样本。

持续记录：

- 冷启动到窗口可见；
- 冷启动到可输入；
- 文件加载耗时；
- 首次所见即所得投影完成耗时；
- 空闲内存和大文件峰值内存；
- 连续输入时的 UI 卡顿。

性能测试至少选择一台普通办公电脑和一台较旧的低配电脑，不能只在开发机上评估。

## 14. 瀑布式增量技术路线

这里的“增量”是指实现顺序按可验证的技术层逐层累加，不是产品敏捷迭代。需求形成版本化受控基线；用户可以提出变更，但必须先完成影响分析、需求升版和设计变更。后置阶段不得在没有变更记录的情况下擅自修改前置接口或删减功能。每个阶段必须通过验收并形成基线，才能进入下一阶段。

### 14.1 第一阶段：需求冻结

先完成：

- 编写逐项功能需求和明确的永久排除清单；
- 定义全部 Markdown 支持矩阵；
- 定义所见即所得操作规则，包括回车、退格、粘贴、跨块选择；

交付物：软件需求规格说明书、支持矩阵、交互规则、验收用例目录。
退出条件：每项需求都有唯一编号、优先级和验收方法，不存在“以后再定”的核心行为。

### 14.2 第二阶段：总体与详细设计

再完成：

- 固化本章的模块依赖和文件清单；

- 为每个公共接口写前置条件、后置条件和错误语义。

交付物：总体设计说明书、详细设计说明书、接口头文件草案、数据结构图、错误码表。
退出条件：可以只依据设计把每个文件分配给 AI，且无需由 AI 自行发明跨模块协议。

### 14.3 第三阶段：工程基础与风险样机

按详细设计搭建：

- CMake、资源、编译选项、测试框架和持续构建；
- 最小 Win32 窗口和 RichEdit 控件；
- MD4C 静态链接和最小语义树；
- 中文 IME、Emoji、DPI 和撤销重做验证；
- 一张本地图片的文内显示；
- 最小 PDF 和 DOCX 文件生成；
- Release 单 EXE 体积与冷启动测量。

这不是对外版本，也不产生临时架构。样机代码只有符合详细设计和测试要求才进入主干，否则废弃并按设计重写。

交付物：风险验证报告、性能基线、依赖许可证清单。
退出条件：所有关键技术风险有实测结论；若结论否定设计，必须退回第二阶段正式修订并重新评审。

### 14.4 第四阶段：底层库实现

依次实现并封闭测试：

1. 编码、换行符、路径和原子文件读写；
2. Markdown 解析、节点模型、索引和校验器；
3. Markdown 序列化和未知块保留；
4. 文档编辑事务和事件；
5. 设置、日志、恢复和最近文件；
6. 图片存储与路径处理。

交付物：不依赖 GUI 的核心静态库及完整单元测试。
退出条件：固定样例能够打开、解析、修改、保存、重开，语义对比全部通过；不得先做界面再补核心模型。

严格按结构由简单到复杂实现：

9. 完整 Markdown 打开和所见即所得投影；
10. Scintilla 源码模式、语法错误定位和保存；
11. 对照模式左侧编辑、右侧只读渲染和同步；
12. 三模式切换、位置恢复、跨模式撤销和版本一致性；
13. 保存后重开一致性及异常回滚。

每增加一种节点，都先完成模型测试、投影测试、输入测试和往返测试，再进入下一种节点。这里的增量只是控制依赖顺序，阶段结束前不会发布一个缺功能版本。

交付物：覆盖完整需求范围的编辑器组件。
退出条件：所有编辑操作矩阵通过，连续输入无模型/视图失步，崩溃和强制关闭后原文件不损坏。

### 14.6 第六阶段：应用外壳与系统集成

在编辑器稳定后实现：

- 主窗口、菜单、工具栏、状态栏和对话框；
- 新建、打开、保存、另存为和最近文件；
- 外部文件修改、只读文件和未保存提示；
- 单实例与命令行打开；
- 文件关联注册、修复、撤销和默认应用引导；
- 浅色、深色、高对比度、多显示器和 DPI；
- 打印及本地设置。

交付物：功能完整但尚未发布的应用程序集成版本。
退出条件：从任意路径运行单 EXE，可合法注册候选程序并完成全部日常文件操作。

### 14.7 第七阶段：PDF 与 DOCX 导出

导出放在编辑和文档模型稳定之后：

- 建立与屏幕无关的导出中间模型；
- 实现 PDF 字体、中文、分页、链接、表格和图片；
- 实现 DOCX 段落样式、编号、表格、图片和关系；
- 对长文档、跨页表格、缺失字体和损坏图片定义行为；
- 使用固定黄金文件进行结构和视觉对比；
- 用 Microsoft Word、WPS 和常见 PDF 阅读器人工验证。

交付物：PDF/DOCX 导出模块和兼容性报告。
退出条件：全部正式语法都能导出，中文不乱码，图片不丢失，文档可被目标软件正常打开。

### 14.8 第八阶段：文档组合、TXT 文档支持与 Windows 文件类型集成

本阶段按 2026-08-12 用户新增要求实施：在光标位置切分为两个新文件、在光标位置插入另一个文件、正式支持 `.txt` 打开保存、为 `.md/.txt` 注册候选程序并引导用户在 Windows 设置中确认默认应用，以及接入应用/Markdown/TXT 三类图标。详细范围和依赖顺序以 `第八阶段新任务接续交接_2026-08-12.md` 及后续冻结的 V05 为准。

交付物：文档组合模块、TXT 文档链路、文件类型设置界面和三类图标资源。
退出条件：V05 逐项验收、Debug/Release 与全量回归通过，原文件和来源文件在组合操作中不受损。

### 14.9 第九阶段：完整系统测试

冻结代码功能，只修复缺陷：

缺陷修复不得顺带增加功能。若缺陷来自设计错误，必须退回相应设计阶段更新基线，再重新执行后续测试。

## 15. 主要风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 原生 Markdown 排版工作量被低估 | 延期、显示不完整 | 需求阶段冻结完整语法矩阵；按依赖顺序实现；建立渲染样例库 |
| RichEdit 投影与语义模型失步 | 保存后内容错误 | 编辑事务、双向位置映射、不变量检查和往返测试 |
| 中文 IME、高 DPI、多屏问题 | 核心用户无法顺畅使用 | 建立专项测试矩阵，尽量使用原生消息与控件 |
| 追求“一个 EXE”限制过多 | 注册路径、资源和数据存储受约束 | 资源静态编译；数据写 AppData；移动后提供关联修复 |
| 需求逐渐变成知识管理软件 | 体积和复杂度失控 | 以“打开、所见即所得编辑、保存、导出”为产品边界 |
| 大文件文档投影卡顿 | 破坏秒开体验 | 分块投影、图片延迟解码和最小范围重新格式化 |
| 自定义图片/表格对象无障碍不足 | 部分用户不可用 | 设计时保留语义节点和 UI Automation 映射 |

## 16. AI 开发的阶段控制

为降低 AI 编程漂移，执行时使用以下硬规则：

1. 需求规格和详细设计是代码的上位依据；AI 不得自行重新解释产品范围。
2. 每个任务必须写明目标文件、允许依赖、接口、输入、输出、错误和验收测试。
3. 一个任务只修改一个文件对或一组不可拆分的强相关文件。
4. 公共头文件先评审、后实现；实现阶段不得擅自扩大接口。
5. 禁止添加未在文件清单和需求规格中的框架、后台服务、网络能力或抽象层。
6. 每个实现任务同时提交测试，测试不得由同一段产品代码自证结果。
7. 阶段验收后生成基线清单和接口快照；后续阶段修改基线必须走设计变更。
8. 遇到未定义行为时停止编码，回到需求或设计文档补充，不允许 AI 猜测。
9. 所有“临时”“TODO”“以后实现”在阶段退出前必须清零或形成经批准的明确排除项。
10. 最终验收按需求编号执行，不以“程序能启动”或“主流程看起来可用”代替。

## 17. 最终建议

马冬梅应从一个边界清楚的 Windows 原生小工具开始：

- 技术上选择 **C++20 + Win32 RichEdit + MD4C + DirectWrite/Direct2D/WIC**；
- 产品上坚持 **默认所见即所得渲染模式，同时提供源码和对照模式，图片可编辑、中文默认、无需配置**；
- 发布物是 **可放在任意目录运行并能注册文件关联的单 EXE**；
- 正式范围内一次完成 Markdown 编辑、PDF 导出和 DOCX 导出；
- 永久不做账号、云服务、插件系统和应用内检查更新；
- 采用需求冻结、详细设计、分层实现、系统测试和最终验收的瀑布式增量开发。

这条路线的开发难度高于套一个浏览器壳，但它与“它就是一个轻量 Markdown 记事本、普通办公人员双击就能用”的目标一致，也能形成马冬梅区别于现有 Markdown 编辑器的核心价值。
