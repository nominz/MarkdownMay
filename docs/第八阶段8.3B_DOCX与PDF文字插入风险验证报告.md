# 第八阶段 8.3B DOCX 与 PDF 文字插入风险验证报告

> 文档编号：MM-PH8-83B-RISK-001
>
> 日期：2026-08-13
>
> 上位需求：`需求规格说明书_V05.md` INSERTX-001～005
>
> 状态：风险样机完成；用户已决定放弃 DOCX/PDF 插入

## 1. 验证目标与硬边界

8.3B 验证 Word/PDF 是否能作为“提取可见文字后插入”的来源。它不承诺复制页面版式、浮动对象、批注、修订或 PDF 页面布局，也不含 OCR。

正式路线必须同时满足：Windows 原生 C++20、离线、不启动 Office、不调用外部 CLI、不运行时下载/释放组件、单 EXE、固定依赖版本、可审计许可证、输入资源上限和中文提取质量。样机中的 Python、`pypdf`、`pypdfium2` 和工作区工具只用于验证，禁止成为产品运行时依赖。

## 2. 样本与方法

| 样本 | 内容 | 验证 |
| --- | --- | --- |
| 压缩 DOCX | H1/H2、中文正文、项目符号、2×2 表格 | ZIP 方法、OOXML 块顺序、中文和结构映射 |
| 文字层 PDF | 中文标题、两段中英混排文字 | 字符数、Unicode 文本、页面渲染一致性 |
| 无文字层 PDF | 页面仅含矢量矩形 | 页面可见但提取字符为 0 |
| 加密 PDF | 由文字层样本生成，禁止无密码打开 | 加密和提取门禁 |

样本位于未跟踪 `tmp/phase83b/`，不作为产品源文件或发布物。DOCX 渲染器因本机未安装 LibreOffice 无法执行；按文档验证规则降级为 ZIP/XML 结构检查。两份 PDF 使用工作区 PDFium 绑定渲染为 PNG，并逐页目视检查。

## 3. DOCX 结果

### 3.1 内容质量

结构提取结果保持原顺序：

1. `Heading1`：八点三B 中文提取样本；
2. 普通正文：中文、English、数字和中文标点完整；
3. `Heading2`：结构标题；
4. 两个 `ListBullet` 项；
5. 表格：`姓名/数量`、`马冬梅/42`。

H1/H2 可映射为 Markdown 标题，普通段落映射为正文，项目符号映射为列表，表格映射为 GFM 表格或在复杂情况下受控降级。首版仍须明确忽略/降级页眉页脚、文本框、批注、修订、脚注、复杂域、多栏和浮动对象。

### 3.2 容器与依赖

真实样本含 17 个 ZIP 条目，全部使用 Deflate 方法 8；解压前总量 827,302 字节，压缩后 34,949 字节。现有 `DocxWriter` 只生成 Store ZIP，不包含通用 Deflate reader，不能反向复用。

候选 `miniz` 3.1.2 是 MIT 许可、可裁剪、支持 ZIP/Deflate 的 C 实现，适合静态编入单 EXE。正式引入前仍须：固定源码与哈希、登记许可证、关闭写入/PNG等非必需模块、限制条目数/单条目/总解压量/压缩比/路径、拒绝加密和 ZIP64 异常、执行畸形包与压缩炸弹测试。

### 3.3 DOCX 决策

DOCX 文字插入通过功能和架构样机，但不得在未批准新依赖时编码。批准 `miniz` 受控引入后，可建立 8.3B-DOCX 条件实现增量；首版只读 `.docx`，不支持旧 `.doc`。

## 4. PDF 结果

### 4.1 门禁与质量

- 文字层样本提取 55 个字符，中文、English、数字和标点与渲染页面一致；
- 无文字层样本页面可见矢量内容，但提取字符为 0，可明确判为无可用文字层并拒绝；
- 加密样本无密码解密返回失败，可在解析前拒绝；
- 视觉检查中，文字层页面无缺字、乱码或重叠，无文字层页面只有矩形。

文字层存在不等于阅读顺序可靠。正式实现还必须覆盖 ToUnicode 缺失、自定义字体编码、对象流、压缩流、多栏、旋转文字、双向文字、隐藏文字、裁剪区、权限、畸形对象和超大页数，不能用只适配简单样本的自制 parser。

### 4.2 候选引擎和体积

PDFium 提供页面字符计数、Unicode 提取和字符坐标 API，采用 BSD 风格许可，技术能力合适。但官方工程使用 Chromium/GN 构建体系并依赖字体、图片、色彩和压缩组件。当前开发运行时的无 V8 `pdfium.dll` 为约 6.88 MB，而当前 Release `MarkdownMay.exe` 约 1.84 MB；仅动态库已为应用体积约 3.7 倍，且正式要求是静态单 EXE。

MuPDF 的开源路线为 AGPL，或需商业授权，不符合当前未建立商业依赖审批的基线。调用 Poppler、Python、Office、外部 CLI 或释放 DLL 均直接违反 V05。

### 4.3 PDF 决策

PDF 的文字层/扫描/加密判定样机通过，但正式 reader 不通过轻量单 EXE门禁。第八阶段不引入 PDFium/MuPDF，不提供 PDF 插入，不做 OCR。未来只有在用户明确接受新的体积预算和 PDF 引擎依赖变更后，才能另立需求与架构变更重新评审。

## 5. 安全与资源上限建议

DOCX 条件实现至少冻结：输入 64 MiB、ZIP 条目 4,096、单条目解压 32 MiB、累计解压 128 MiB、压缩比 100:1、XML 深度 128、文本节点 1,000,000、超时/取消门禁；ZIP 路径禁止绝对路径和 `..`，不释放包内容到磁盘。

PDF 若未来重启评审，至少冻结：输入 100 MiB、页数 2,000、对象数/字符数/页面尺寸上限、密码和权限策略、逐页取消、零文字页比例、Unicode 替换字符比例、阅读顺序质量阈值和沙箱/模糊测试。

## 6. 追溯结论

| 需求 | 结论 |
| --- | --- |
| INSERTX-001 DOCX | 样机通过；等待 `miniz` 依赖批准后条件实现 |

| INSERTX-004 安全/无外部程序 | DOCX 有可行静态路线；PDF 当前候选不满足体积边界 |
| INSERTX-005 先样机后实现 | 已遵守；未把开发运行时工具写入产品代码 |

## 7. 最终建议

2026-08-13 用户最终选择放弃 DOCX 与 PDF 插入。因此不批准 `miniz`，不启动 8.3B-DOCX 实现，PDF reader 也不再作为延期待办。产品继续清楚提示仅支持 `.md/.markdown/.txt`；不以“能检测文字层”为由自制不完整 parser，也不把 Python/Poppler/PDFium DLL 当成隐藏运行时依赖。
