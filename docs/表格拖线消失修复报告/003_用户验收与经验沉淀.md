## 最终解决方式

### 原因一：WM_SIZE 内原位更新失败

旧实现最大化后在 RichEdit `WM_SIZE` 布局栈中使用缓存 `cpStartRow` 对全部 rows 调用 `EM_SETTABLEPARMS`。真实 trace 显示该调用在 2044/2539px 宽度下失败。

### 原因二：最大化宽度直接转换为累计 cellx

旧实现让 table 宽度等于整个 formatting rect。窗口越宽，累计 `cellx` 越大，最终超出 RichEdit 原生表格的稳定工作范围；后续 `EM_INSERTTABLE` 也失败。

### 修复

1. `WM_SIZE` 内不再原位修改原生 rows；
2. 布局消息返回后合并执行一次完整重建；
3. 重建前用空 RTF 清除旧 table tree；
4. 从 `DocumentSession` 重新投影 native tables；
5. 原生表格最大逻辑宽度限制为 14,400 twips；
6. Markdown 源码和 `---` 数量不承担 GUI 列宽持久化。

## 为什么前几轮没有解决

前几轮共同假设是：

```text
拖线
→ column tracker / EN_CHANGE
→ flat mapping
→ 表格消失
```

因此修改集中在：

- 内外列线命中；
- DPI tolerance；
- cursor/capture；
- caret 是否仍在 Cell；
- 延迟同步手势状态；
- 格式变化后的恢复。

这些工作没有首先检查最大化时 `EM_SETTABLEPARMS` 和恢复时 `EM_INSERTTABLE` 的真实返回值，所以始终没有触及主因。

## 固化的工程规则

以后处理 RichEdit 原生结构缺陷必须遵守：

1. 先记录真实 Windows 消息顺序；
2. 记录所有关键 Win32/TOM API 返回值；
3. 分别统计 Markdown nodes、projection tables、TOM native tables；
4. resize 测试必须经过真实 `WM_SIZE` 和消息泵；
5. 必须包含最大化/高 DPI/超宽窗口；
6. 合成 TOM2 测试不得冒充用户场景验收；
7. 没有新证据，不得继续增加同类拦截补丁；
8. 用户真实流程通过后才允许关闭缺陷。
