## 与此前各轮的区别

此前各轮从画面推断 column tracker、caret、cursor、capture 或 `EN_CHANGE`，然后直接修改行为。本轮不新增另一种拦截猜测，而是记录真实程序的消息与状态序列，以决定下一轮应修改正文同步、原生结构还是布局层。

## 本轮新增证据能力

Release 运行时写入：

```text
%TEMP%\MarkdownMay_table_trace.log
```

日志包含：

- ViewMode host 的 `WM_SIZE`；
- RichEdit 的 `WM_SIZE`、`WM_LBUTTONDOWN`、`WM_LBUTTONUP`、`WM_CAPTURECHANGED`；
- 鼠标消息发生时 RichEdit 是否持有 capture；
- `EN_CHANGE` 在父窗口到达的时刻；
- posted sync 实际分发的时刻；
- `note_change_notification()` 看到的临时只读、capture、resize cursor 状态；
- `synchronize_change()` 进入的分支；
- 同步前的 `DocumentSession.source_revision`、table projection 数量；
- `project()` 开始/结束、原生表格插入失败；
- resize 时 `SetNativeTableParameters(..., insert=false)` 的调用和结果；
- RichEdit 控件尺寸及最终文本长度。

## 真实日志结论

用户按要求完成真实复现。关键日志为：

```text
host WM_SIZE width=2560 height=1272
resize refresh begin width=2539 height=1268 tables=9
resize refresh end result=0
resize refresh begin width=2044 height=1268 tables=9
resize refresh end result=0
...
sync branch=pending_native_format reproject
project begin revision=2
project insert_tables failed tables=9
```

结论：

- `DocumentSession.source_revision` 始终为 2；
- projection 始终识别 9 张表；
- 最大化时原位 `EM_SETTABLEPARMS` 已连续失败；
- 拖动后清空恢复时 `EM_INSERTTABLE` 再次失败；
- 问题属于 RichEdit 原生 table 结构/宽度参数失败，不是 Markdown 正文被改坏；
- 此证据否定了此前把主要精力放在 `EN_CHANGE` flat mapping 的方向。

另一个真实现象是非最大化拖动前两次跳到文档开头。日志显示一次手势触发多次 `project()`；该问题作为后续独立事项保留，不能与“最大化后全部表格消失”混为同一验收结论。
