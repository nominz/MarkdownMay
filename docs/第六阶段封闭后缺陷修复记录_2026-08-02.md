# 第六阶段封闭后缺陷修复记录

> 记录编号：MM-DEFECT-2026-001
> 日期：2026-08-02
> 基线：`155d9c4 feat: close phase 6 application integration`
> 范围：封闭阶段实现偏差修复，不改变 V02 产品范围

## 1. 缺陷与既有需求

| 缺陷 | 用户可见问题 | 既有需求 | 结论 |
| --- | --- | --- | --- |
| BUG1 | 渲染文档区没有动态垂直滚动条，鼠标滚轮无效 | EDIT-002、EDIT-008、UI-013～014 | 已有交互能力的实现缺陷 |
| BUG2 | 菜单栏、弹出菜单和菜单项过矮，不符合 Win11 记事本式体验 | OBJ-007、UI-009、UI-013～014 | 已有 UI/DPI 要求的视觉实现缺陷 |
| BUG3 | 打开 Markdown 时滚动到文末且加载期间不可操作 | OBJ-001、PERF-002、EDIT-010C | 打开位置和投影行为缺陷 |
| BUG4 | 渲染模式输入 `---` 不即时显示分隔线 | EDIT-002、EDIT-004、EDIT-010A、MD-011 | 所见即所得同步缺陷 |

上述四项均不新增产品能力，不修改 V02 冻结需求；修复继续以唯一 `DocumentSession` 为状态源。

## 2. 修复设计与实现

- BUG1：渲染 RichEdit 增加 `WS_VSCROLL`，由系统按内容范围动态显示/隐藏；增加明确的 `WM_MOUSEWHEEL` 子类处理，按每个滚轮刻度三行滚动。
- BUG2：菜单改为 Win32 owner-draw；96 DPI 基准菜单项约 33 px、菜单字体 14 px，并随 DPI 缩放；选中、禁用及高对比度颜色继续取系统颜色。
- BUG3：投影前保存选区和滚动位置，投影后恢复；文件重载前后显式把选区和视口置于文首，删除原先每次投影强制选中文末的行为。
- BUG4：RichEdit 订阅 `ENM_CHANGE`；收到 `EN_CHANGE` 后向 UI 消息队列投递同步，待当前按键完成后提交到 `DocumentSession` 并重新投影，避免在光标尚未更新时重入。

## 7. 第三轮用户复测修正（2026-08-03）

用户复测发现：在渲染模式输入两个空行后键入单独的 `*`，源码正确但项目符号被投影到上一段末尾，并产生可放置插入点的异常空白；同时原生非客户区菜单栏仍受 Windows 系统高度限制，未达到记事本的菜单行高度，顶层悬停区和下拉菜单也缺少 Win11 圆角观感。

本轮修正：

- Markdown 解析后的范围修复增加空列表项处理：从当前解析游标定位真实的 `-`、`*`、`+` 列表标记行，修正零长度 `list_item` 及父 `list` 的 `SourceRange`。渲染投影继续只读取 `DocumentSession` 的语义文档与源码，不建立第二套正文状态。
- 顶层菜单从受非客户区系统度量限制的 `HMENU` 菜单栏改为客户区原生子控件菜单栏，96 DPI 基准高度 36 px，宽度按各标签实测文字宽度加边距计算；悬停/按下背景使用浅灰圆角矩形。
- 下拉菜单项不再 owner-draw，恢复由 Windows 11 系统菜单绘制，以采用系统弹出窗口圆角、高亮、阴影和辅助功能行为；既有命令 ID、状态查询和快捷键表保持不变。
- 主窗口布局把菜单栏高度显式计入工具栏与文档区的纵向起点，避免新增菜单栏覆盖工具栏或正文。

自动验证：

- `MarkdownMayFullProjectionUnit` 增加“段落 + 空行 + 单独 `*` + 后续标题”回归，验证项目符号位于段落和标题之间、源码映射落在真实星号位置且不产生异常连续空行。
- `MarkdownMayAppShell` 验证主窗口不再安装受系统限制的非客户区菜单、客户区菜单栏不低于 36 DPI 缩放像素，以及文档区布局包含菜单栏高度。
- Debug、Release 的 `MarkdownMayFullProjectionUnit` 与 `MarkdownMayAppShell` 均返回 0；Debug/Release 主程序构建成功。
- Debug 完整回归为 34/36：本轮直接相关测试全部通过；既有 `wysiwyg_block_integration` 在撤销断言处稳定返回 6，既有 `wysiwyg_input_integration` 本轮出现一次输入时序失败。两项均如实保留为未通过，不记为 36/36，后续需单独诊断其与本轮变更的关联。

## 8. 客户区菜单不可见紧急修正（2026-08-03）

第三轮提交把 owner-draw 顶层菜单按钮错误地创建为背景 `STATIC` 栏的子控件，导致 `WM_DRAWITEM` 和 `WM_COMMAND` 发往背景栏而非主窗口；Release 实际运行只显示空白菜单区域。修正为背景栏与六个菜单按钮均直接隶属主窗口，按钮保持在背景栏上方，绘制和点击消息由主窗口统一处理。

应用外壳回归新增真实控件路径断言：必须能通过主窗口 ID 9000 取得“文件”按钮，按钮父窗口必须是主窗口且标题必须包含“文件”。重新构建并直接运行 Release `MarkdownMayAppShell` 返回 0；目标 Release 主程序已在用户指定路径重新生成。

## 12. 列表退出触发与逐键输入性能修正（2026-08-08）

用户按完整顺序复测发现：无序列表空项回车退出后，输入单独 `1` 被视觉上提前转换为有序列表；同时约 15 KB 业务文档中逐键输入存在 1～4 秒停顿。登记为 DEF-018、DEF-019。

- 列表回归严格覆盖“段落回车→`*`→空格→正文→回车续项→空项回车退出→输入 `1`”，并同时断言 `DocumentSession` 源码和 RichEdit 可见文本；单独 `1` 保持普通文本，不出现 `1. ` 合成编号。
- 性能根因为普通字符每次提交后都调用 `SetWindowTextW` 重写全文并重新应用全部格式。同步仍提交唯一 `DocumentSession` 并解析 Markdown，但先构建下一投影；当可见文本与格式结构未变化时，仅替换投影映射，不重写 RichEdit 全文。
- 形成列表、标题、强调、分隔线等格式结构时，格式结构签名发生变化，仍执行完整投影，保持即时所见即所得。
- 性能回归使用约 15 KB、100 个实际长度段落，普通中文字符同步阈值为 750 ms；Debug 连续 5 次及 Release 连续 5 次均通过。
- Debug 完整回归 35/36；唯一失败仍为既有 `wysiwyg_block_integration` 撤销断言。其余结构输入、完整投影、列表与三模式测试通过。
- Release 主程序与段落/性能、完整列表序列直接测试构建成功；Release 直接测试全部返回 0。
- Release 程序：`build/windows-x64-debug/app/Release/MarkdownMay.exe`，1,629,184 字节，SHA-256 `FE1D813A24560BF429B0A0DE654C7E21A8327B276313F8234B57873D606E5BEB`。

## 13. 对照切换稳定性与 Win11 界面轻量化修正（2026-08-08）

用户报告在渲染模式输入后进入对照模式、于源码左栏加入一级标题并确认右栏更新，再返回渲染模式时窗口卡死；同时要求工具栏、状态栏和退出保存提示贴近 Win11 记事本的轻量视觉。登记为 DEF-020～DEF-023。

- 模式切换现在具有明确的内部同步边界：切换期间 RichEdit 完整投影产生的 `EN_CHANGE` 不再排队触发第二次正文同步，非渲染模式下遗留的渲染同步消息也不再执行。
- `view_modes_integration` 严格增加“渲染输入→对照模式→源码插入 `# 标题1`→右栏确认标题→返回渲染”的流程，要求返回过程不超过 1 秒且标题存在。
- 工具栏移除直接显示的中文按钮文字，以 Windows `Segoe Fluent Icons` 图标字体绘制；命令中文名称和快捷键继续由工具提示提供。悬停、按下和选中状态绘制 DPI 感知的小圆角背景。
- 状态栏保持原生状态栏文本接口与五个信息分区，但采用 12 px DPI 感知水平内边距和上下收短的浅色分隔线，高度保持 24 px。
- 未保存文档退出提示由旧式 `MessageBox` 改为系统 `TaskDialogIndirect`，使用“保存／不保存／取消”按钮，由 Windows 11 系统主题提供圆角、字号和间距。
- Product Design 截图对照流程影响了工具栏按钮尺寸、状态栏留白和交互态取值；Windows 自动化插件因本机 `EPERM` 无法初始化，且单实例环境中已有窗口导致独立 Debug 截图无法取得，因此像素级视觉验收如实保留为待用户复测，不宣称自动视觉通过。

验证结果：

- Debug 全量构建成功；完整回归 32/36。`wysiwyg_block_integration` 为既有撤销断言失败，`wysiwyg_input_integration` 为既有输入时序波动，`startup_single_instance_integration` 受当时运行中的旧版马冬梅进程影响；`app_shell_integration` 在新增工具栏尺寸断言调整后单独复跑通过。本轮核心 `view_modes_integration` 与 `app_shell_integration` 均直接通过。
- Release 主程序、模式切换和应用外壳测试目标构建成功；`MarkdownMayViewModes`、`MarkdownMayAppShell` 均返回 0。
- Release 程序已由下节启动兼容性紧急修正重新生成，最终尺寸和校验值以下节为准。

## 14. 现代任务对话框启动兼容性紧急修正（2026-08-08）

用户启动上一版 Release 时，Windows 加载器提示“无法定位序数 345 于动态链接库 MarkdownMay.exe”，程序无法进入主窗口。登记为 DEF-024。

- 根因是上一轮直接调用 `TaskDialogIndirect` 形成了对 `comctl32` 序号 345 的加载期静态依赖，而应用清单没有声明 Common Controls v6；因此加载器在进入 `wWinMain` 前即失败。
- 应用清单现明确声明 `Microsoft.Windows.Common-Controls` 6.0；退出确认同时改为通过 `GetProcAddress` 运行时检测 `TaskDialogIndirect`，不再产生加载期序号依赖。若现代任务对话框不可用，则安全回退 `MessageBoxW`。
- Release 主程序、`MarkdownMayViewModes` 和 `MarkdownMayAppShell` 构建成功，两个直接测试均返回 0。
- 最终 Release 真实启动验证：启动 5 秒后进程仍存活、`Responding=True`，已建立 8 个线程；确认不再发生加载器序数错误。验收进程为空白文档，验证后已关闭。
- 最终 Release：`build/windows-x64-debug/app/Release/MarkdownMay.exe`，1,633,280 字节，SHA-256 `7B8523D2CE1DB390C6E1948AE95A26ED107360C12B5982CF219BE8BBD8F24CEC`。
