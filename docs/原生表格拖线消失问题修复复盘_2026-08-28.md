# 原生表格拖线后全部消失问题修复复盘

日期：2026-08-28

## 1. 用户可稳定复现的事实

复现文件：`docs/需求规格说明书_V04.md`。

复现步骤：

1. 确认任务管理器中没有马冬梅进程；
2. 启动 `build/windows-x64-debug/app/Release/MarkdownMay.exe`；
3. 通过“文件 → 最近文件”打开 V04；
4. 初始非最大化窗口中拖动表格线，表格不消失；
5. 最大化窗口；
6. 拖动表格线；
7. 不只是当前表格，文档中的所有表格都消失。

用户已经通过文件属性截图确认测试文件为 2026-08-28 10:00:59、2,765,824 字节的构建，并确认启动前没有旧进程。因此“测错 EXE”“旧进程未退出”“单实例转发到旧版本”均不能再作为解释。

## 2. 当前仍未得到证据回答的问题

以下问题此前被当作结论，但实际上没有从真实复现中取得运行证据：

- 拖动时 RichEdit 是否真的发送了 `EN_CHANGE`；
- `EN_CHANGE` 到达时 selection、capture、cursor、控件只读状态分别是什么；
- 表格消失前是否先发生 `WM_SIZE`、`EN_REQUESTRESIZE`、`EM_SETRECT` 或 `EM_SETTABLEPARMS`；
- 消失的是 RichEdit 原生 table 结构，还是 `DocumentSession` 中的 Markdown table 源码；
- `RichEditHost::project()` 是否被调用，返回值是什么；
- `SetNativeTableParameters(..., insert=false)` 是否在最大化后的布局栈或拖动期间失败；
- 表格消失后保存文件，Markdown 管道符表格是否仍在；
- 问题是否由绘制/布局消失造成，而非同步层写坏正文。

在这些问题没有日志证据前，“原生列宽 tracker 导致 flat mapping”只能算候选根因，不能再当作已确认根因。

## 3. 原生 Cell 化的起点

### `cece9cb`：迁移 Markdown 表格到 RichEdit 原生 Cell

目标是解决原先“一行 paragraph + tabs”导致各列无法独立换行的问题。表格改为 RichEdit native table/cell，Markdown 与 `DocumentSession` 仍为唯一正文。

这次架构改动建立了真正的 Cell，但同时引入两个必须严格处理的新边界：

- RichEdit 自己维护的 RTF table 结构字符；
- 应用投影、窗口 resize、RichEdit 内部 table layout 三者之间的重入和同步时序。

当前拖线消失问题发生在这次迁移之后。

## 4. 历次修复及其局限

### 4.1 `bac65bd`：resize 时保留原生表格

修改点：

- 禁止在 RichEdit 的 `WM_SIZE` 布局栈内直接完整 `project()`；
- `refresh_layout_after_resize()` 改为对现有表格调用 `EM_SETTABLEPARMS`；
- 同一提交还修复了只读文件打开、标题栏和状态栏只读状态。

当时假设：最大化时完整重投影发生重入，导致 `EM_INSERTTABLE` 失败，只剩平坦文本。

结果：解决了“最大化后表格直接消失”的一部分现象，但最大化后拖线仍使表格消失。

局限：没有记录真实拖线过程中 `WM_SIZE`、`EM_SETTABLEPARMS` 和 `project()` 的调用序列及返回值。

### 4.2 `8a8e84a`：拦截内部列线调整

修改点：

- 使用 `TableLayout.column_boundaries` 判断内部列线；
- 在 `WM_LBUTTONDOWN/WM_LBUTTONDBLCLK/WM_SETCURSOR` 阻止 RichEdit 原生列宽调整。

当时假设：问题是 RichEdit 的内建列宽 tracker 修改了仅存在于 RTF 的列宽，之后进入错误同步。

结果：用户实测未解决。

局限：命中测试依赖投影和 TOM 推导的缓存几何，没有证明它与最大化后的 RichEdit 实际 hot zone 一致。

### 4.3 `090327d`：补拦左右外边界

修改点：

- 从只拦内部列线扩展为同时拦截表格左右外边界；
- 扩大 DPI 命中容差。

当时假设：最大化后暴露了窄窗口中不可拖动的 table right edge。

结果：用户实测未解决。

局限：仍然只是扩大同一套几何命中，没有证明用户拖动位置走到了这些分支。

### 4.4 `f8144b4`：格式变化后清空 RTF tree 并重投影

修改点：

- 增加纯格式变化识别；
- 用空 RTF stream 清除 RichEdit 残留 row/cell 结构；
- 延迟调用 `project()` 从 `DocumentSession` 重建原生表格；
- 放宽 Cell physical position 漂移后的映射；
- 增加直接 TOM2 `ITextRow::SetCellWidth()` 的集成测试；
- 测试真实 V04 可建立 9 张表。

当时假设：即使没有成功拦住 tracker，只要 Cell 可见文本未变，就可以安全恢复原生结构。

结果：用户实测未解决。

局限：测试直接调用 TOM2 改宽，并由测试显式调用 `synchronize_change()`，没有复现真实窗口消息顺序；“表格仍有 20 个 Cell”也不等价于真实最大化窗口拖动后仍可见。

### 4.5 `a1bbc81`：selection 可离开表格、扩大 hot zone

修改点：

- 不再要求同步发生时 caret 仍在原生表格内；
- 扩大列线容差；
- 使用系统水平 resize cursor 作为补充判据；
- 回归测试把 selection 移到表格外。

当时假设：最大化后的 tracker 在通知前移动了 selection，导致上一版识别失败。

结果：用户实测未解决。

局限：仍然把 selection/cursor 当作 tracker 的可靠证据，没有真实日志支持。

### 4.6 `3767dbd`：实时 TOM Cell 命中

修改点：

- 鼠标点通过 `EM_CHARFROMPOS` 转为当前 cp；
- 通过 TOM2 `Expand(tomCell)` 和 `GetRect(tomCell)` 获取实时 Cell 矩形；
- 不再只依赖最大化前缓存的 `TableLayout`/projection cp。

当时假设：最大化后缓存几何与 RichEdit 实际 hot zone 偏离。

结果：用户实测未解决。

局限：仍在“鼠标按下前拦住 tracker”这一条路径内迭代，没有证明真正致因是这一条消息路径。

### 4.7 `f219d03`：RichEdit 持有 mouse capture 时拒绝同步

修改点：

- 文档含原生表格且 RichEdit 正持有 mouse capture 时，`synchronize_change()` 不执行整篇 flat mapping；
- 直接从 `DocumentSession` 恢复投影。

当时假设：列宽 tracker 的 `EN_CHANGE` 会在 RichEdit 持有 capture 时同步。

结果：用户实测未解决。

局限：真实程序不是同步执行 `synchronize_change()`，而是先 `PostMessage`。测试却让 capture 一直保持到同步调用，验证了错误时序。

### 4.8 `9796424`：原生 Cell 鼠标手势期间临时只读

修改点：

- 鼠标在原生 Cell 中按下后临时 `EM_SETREADONLY(TRUE)`；
- `WM_LBUTTONUP/WM_CAPTURECHANGED` 后恢复；
- 目标是在源头禁止 RichEdit 修改原生 table 格式。

结果：用户实测未解决。

局限：仍然依赖我们的 point/cell 命中和对 RichEdit 内部 tracker 时序的推断；没有证据表明临时只读分支在用户复现时实际执行。

### 4.9 `fbd4a29`：跨延迟同步保存手势状态

修改点：

- `ViewModeController` 收到 `EN_CHANGE` 时立即调用 `note_change_notification()`；
- 保存 capture/cursor/表格手势状态；
- posted `synchronize_change()` 稍后消费标记；
- 测试改为“通知时有 capture → 释放 capture → 延迟同步”。

当时假设：此前失败的核心是异步消息使瞬时状态丢失。

结果：用户实测未解决。

局限：虽然修正了测试时序，但仍未证明真实拖线确实产生了满足条件的 `EN_CHANGE`，也未检查另一条 resize/reformat 调用链。

## 5. 我们一直在绕的圈子

后六轮修复虽然代码点不同，但共享同一个未经证实的故事：

```text
用户拖动列线
→ RichEdit 原生 column tracker 修改 RTF table
→ EN_CHANGE
→ flat source mapping
→ 所有表格消失
```

随后所有工作都在这个故事内部变化：

- 扩大边界命中；
- 增加外边界；
- 改用 cursor；
- 改用 capture；
- 改用实时 TOM Cell rect；
- 临时只读；
- 保存异步通知时的瞬时状态；
- 事后清空 RTF tree 并重投影。

这确实是在一个圈子里打转。最大的过程错误不是某一行代码，而是：**没有先用真实复现的运行轨迹确认上述因果链，就连续提交了多轮修复。**

## 6. 自动测试为什么连续给出假安全感

现有 `wysiwyg_table_integration` 的相关测试存在这些缺口：

- 通过 TOM2 直接调用 `SetCellWidth()`，不是实际鼠标拖动；
- 测试自行控制 selection、cursor 和 capture；
- 部分版本直接调用 `synchronize_change()`，没有经过 `ViewModeController` 的真实 posted-message 队列；
- 没有从 Windows 顶层窗口执行“非最大化 → 最大化 → 实际鼠标拖动”；
- 没有记录 `WM_SIZE` 与 RichEdit 通知的先后顺序；
- 主要断言是 Markdown 未变和 Cell 数量仍在，缺少最终可见性/绘制断言；
- 没有验证 V04 中 9 张表在真实拖动之后全部仍可见。

因此“Debug/Release 表格专项测试通过”只能证明合成场景通过，不能作为该用户缺陷已修复的证据。此前把它表述为修复完成是不准确的。

## 7. 现在需要跳出的方向

下一轮不能再先写修复，必须先得到一次真实复现的结构化 trace。建议增加仅 Debug/诊断构建启用的环形日志，至少记录：

1. 顶层窗口 `WM_SIZE` 前后尺寸和最大化状态；
2. RichEdit subclass 的 `WM_SIZE`、`WM_LBUTTONDOWN/UP`、`WM_MOUSEMOVE`、`WM_CAPTURECHANGED`；
3. 鼠标坐标、`EM_CHARFROMPOS` cp、`Expand(tomCell/tomTable)` 结果、Cell rect；
4. `EM_SETREADONLY` 前后状态；
5. 父窗口收到的全部 RichEdit `WM_COMMAND/WM_NOTIFY` code，而不只 `EN_CHANGE`；
6. `note_change_notification()` 是否命中及原因；
7. posted `synchronize_change()` 执行时间和进入的具体分支；
8. 同步前后 `DocumentSession.source_revision`、源码字节数、Markdown table 节点数；
9. `refresh_layout_after_resize()` 的进入次数；
10. 每次 `EM_SETTABLEPARMS` 的 table/row、`cpStartRow`、返回 HRESULT；
11. 每次 `project()`、`ResetRichEditDocument()`、`EM_INSERTTABLE` 的结果；
12. 操作前后 RichEdit 中 TOM `tomTable/tomCell` 的实际数量和可见矩形。

日志必须能区分三种结果：

- **正文损坏**：`DocumentSession` 中 table nodes 从 9 变为 0；
- **原生结构损坏**：正文仍有 9 张表，但 RichEdit TOM table/cell 消失；
- **布局/绘制损坏**：正文和 TOM Cell 都存在，但 rect 为空、离屏或未绘制。

只有先确定属于哪一种，才能选择正确层修改。

## 8. 下一步候选根因（仅列为待证伪假设）

以下方向不能再直接实施，必须由 trace 选择：

### A. `refresh_layout_after_resize()` 重入或错误更新全部 rows

最大化会触发 `WM_SIZE → EM_SETRECT → refresh_layout_after_resize() → EM_SETTABLEPARMS`。拖线可能再次触发布局，使全部表格 row 参数在 RichEdit 内部布局栈中失效。这条路径能解释“只有最大化后”和“所有表格一起消失”，但目前没有调用日志。

### B. posted source sync 把结构标记写回正文

这仍是候选，但必须通过 source revision/table-node-count 变化确认，不能再从画面推断。

### C. TOM physical cp 在最大化重排后整体失效

`refresh_layout_after_resize()` 继续使用 projection 中保存的 `physical_begin/cpStartRow`。如果 RichEdit 在最大化时改变结构位置，后续对错误 `cpStartRow` 调用 `EM_SETTABLEPARMS`，可能破坏多张表。

### D. 表格仍存在但几何被更新到零宽、超宽或离屏

如果 TOM table/cell 数量未变而画面消失，应调查 `dxWidth/cellx`、formatting rect、DPI 与水平滚动，而不是 source mapping。

### E. RichEdit 内建 table UI 的消息不是我们假设的鼠标/EN_CHANGE 序列

可能走 `WM_NOTIFY`、OLE/TOM 内部事务或其他格式通知。必须记录全部通知 code 才能确认。

## 9. 本次复盘结论

1. 缺陷仍未解决。
2. 用户测试文件、文件时间和进程状态已经确认正确。
3. 历次修复大多围绕同一个未经真实 trace 证实的 column-tracker/`EN_CHANGE` 假设。
4. 合成 TOM2 测试不能替代真实最大化窗口鼠标拖动。
5. 下一步应先增加可审计诊断日志并让真实复现产生证据。
6. 在确认是正文、原生结构还是布局绘制哪一层损坏前，不应再提交功能性修复。
